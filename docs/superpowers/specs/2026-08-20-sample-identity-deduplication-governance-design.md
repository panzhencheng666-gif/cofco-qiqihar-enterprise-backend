# 样本点身份防重与历史归并治理设计

## 目标

在不改变既有填报、业务审核、核定数据发布和实时分析公式的前提下，为产情与市场 XLSX 导入增加样本点身份防重，并为现存重复身份提供可导出、可复核、可回放的原位归并链。

完成后必须满足：

- 新导入不会因为姓名相同就直接拒绝，也不会因为姓名相同就自动合并。
- 明确属于同一对象的行复用既有稳定样本点 ID。
- 明确属于不同对象的行允许继续创建新样本点。
- 证据不足或互相冲突的行保留为导入草稿，状态显示为“身份待核验”，不进入正式业务审核、总揽、分析或供需统计。
- 身份核验决定完成后，原草稿自动继续进入原有提交与业务审核链，不要求整份 XLSX 重导。
- 历史归并保留业务记录、版本和事实值，只通过现有追加式身份解析修订把记录指向一个规范样本点。

## 范围与约束

- 后端使用 JDK 21；Web 使用 Node 24。
- 测试写入仅允许 `qiqihar_enterprise_test`。
- 不新增通用身份表或简单唯一索引；实现阶段仅允许 V129–V131 三个受审迁移：统一可见身份的有效记录口径、增加经审核才能调用的追加式归并入口，并给该入口的 NOLOGIN 所有者补足嵌套校验所需的最小只读权限。它们继续复用 `platform.business_import_draft`、不可变 `platform.business_audit_event`、`platform.business_event_outbox` 与 `registry.sample_subject_resolution_*`。
- 不提交、不暂存、不重置、不清理共享工作树。
- 不修改供需公式，不把缺失值改成 0，不创建虚构物流数据。
- 不删除历史业务记录或历史样本点主数据。
- 坐标重复与身份重复是两个相邻但独立的治理判断；身份决定不得绕过坐标冲突校验。
- 普通账号继续执行职责分离；平台唯一所有者沿用服务器端既有特权例外，但每次自审仍写不可变审计。

## 现状与问题

当前核定时已经存在一部分可见身份复用逻辑：姓名和联系方式唯一命中时复用样本点，无命中时新建；多个命中或位置冲突时在最终审核阶段抛出业务冲突。该行为有三个缺口：

1. 冲突出现得太晚，用户在审核最后一步才知道身份有问题。
2. XLSX 行没有“身份待核验”工作状态，无法只隔离问题行并继续处理其他行。
3. 历史重复身份虽已有追加式解析数据库能力，但没有业务服务、工作簿和 Web 审核入口。

## 身份与记录的业务定义

### 稳定样本点身份

样本点 ID 是服务器内部的稳定编号。姓名仅用于展示，不能作为唯一键。联系方式、地区、坐标、对象类型和历史来源是判定证据，不是任何一个字段单独决定身份。

同一个真实对象跨产品、跨年月产生多条业务记录时，业务记录 ID 可以不同，但应复用一个稳定样本点 ID。

### 同期业务记录重复

身份相同、业务域相同、产品相同且处于同一治理期间时：

- 事实字段相同：属于重复导入，不再创建第二条正式记录。
- 事实字段不同：属于业务事实冲突，保留草稿并提示使用原记录修正或人工核验，不能自动覆盖、相加或选择一条丢弃。

跨年月的同一身份不是重复身份；它是同一身份下的不同业务记录。

## 三态身份判定

新增 `SampleIdentityAssessment`，结果只允许三类：

### `MATCHED`

满足强匹配且只有一个有效候选：

- 规范化姓名相同；
- 非空联系方式规范化后相同；
- 候选样本点只有一个；
- 地区与坐标同现有核定位置兼容。

结果：自动复用候选稳定样本点。正常填报、提交、审核与发布不增加一步操作。

### `DISTINCT`

不存在强匹配候选，且已有同名候选能够被非空联系方式、地区和位置证据明确区分。

结果：允许按原有流程创建新的稳定样本点。姓名相同本身不会阻断。

### `REVIEW_REQUIRED`

出现任一情况：

- 同一规范化姓名和联系方式对应多个有效样本点；
- 姓名、联系方式、地区或坐标证据互相冲突；
- 姓名相同但联系方式缺失或不足以区分；
- 同一导入任务内出现相同身份和期间的冲突行；
- 同身份同期间已存在正式记录，但本次事实与原记录不同。

结果：行写入 `platform.business_import_draft`，不晋级为正式业务记录。响应使用业务状态和中文原因，不返回 500 或笼统的“导入失败”。

## 导入与在线填报流程

### XLSX 导入

1. 解析和现有字段校验保持不变。
2. 在 `ImportDraftRowExecutor` 晋级前执行身份与同期记录判定。
3. `MATCHED` 或 `DISTINCT` 行继续调用既有 `createAndSubmit`。
4. `REVIEW_REQUIRED` 行只调用新增的 `createPendingIdentityReview`，保留为 `DRAFT`。
5. 导入任务该行仍记为已接收，但附带 `SAMPLE_IDENTITY_REVIEW_REQUIRED` 警告、草稿 ID 和可读原因；其他行不受影响。

### 在线填报

在线记录提交前复用同一判定器。明确结果不改变按钮和流程；待核验结果以业务冲突阻止提交，并返回可直接进入身份核验工作台的中文说明。在线草稿本身继续保留，不丢失用户输入。

### 人工决定

身份工作台对一个待核验草稿提供三种操作：

- `LINK_EXISTING`：选择一个候选样本点 ID，并填写依据。
- `CONFIRM_DISTINCT`：确认是不同对象，并填写依据。
- `RETURN_FOR_CORRECTION`：说明原行有误，保留草稿待修改。

决定写入不可变 `platform.business_audit_event`。聚合类型使用 `SAMPLE_IDENTITY_REVIEW`，聚合 ID 使用导入草稿 ID；事件详情包含候选快照、目标样本点、地区、产品、导入任务、源行、理由和决定版本。

`LINK_EXISTING` 和 `CONFIRM_DISTINCT` 决定写入后，服务在同一事务中重新判定当前候选和草稿版本，再晋级原草稿。晋级后的业务记录写一条关联审计，使最终业务审核能够取得经核验的目标或“明确不同”决定。候选或草稿发生变化时拒绝过期决定，要求刷新，不静默套用旧结论。

### 正式审核

产情与市场 `linkApprovedSamplePoint` 先读取当前业务记录的身份决定：

- 有有效 `LINK_EXISTING`：校验目标仍为有效、地区/坐标兼容的核定样本点后链接。
- 有有效 `CONFIRM_DISTINCT`：跳过姓名模糊候选，但仍执行地区、坐标边界和重复坐标保护，再按原流程创建样本点。
- 无人工决定：继续使用自动三态判定；唯一强匹配复用，无匹配新建，多候选或位置冲突保持业务阻断。

因此正常填报审核无新增错误；原本最终审核才暴露的身份冲突被提前变成可恢复工作项。

## 历史身份归并

### 候选导出

服务端按规范化姓名、联系方式、域、期间、样本点 ID、地区和坐标生成历史候选。导出工作簿至少包含：

- 记录 ID、记录版本和状态；
- 当前样本点 ID 与规范样本点候选；
- 姓名、联系方式、地区、坐标、业务域、产品和期间；
- 导入任务和源行（可追溯时）；
- 只读行绑定、导出批次和输入摘要；
- 处理方式、规范样本点、核验依据和备注。

工作簿只允许 `归并至规范样本点`、`保留为不同身份`、`暂不处理`。只读字段、版本和批次被篡改时该行失败，不影响其他行。

### 上传与审核

上传只创建身份归并请求，不直接修改记录。请求通过 `platform.business_audit_event` 持久化并支持历史、失败行和幂等重试。审核队列显示全部来源记录、当前与目标样本点、前后身份及依据。

普通提交人不能审核自己的请求；平台唯一所有者可按现有例外自审。批准前重新校验版本、状态、目标样本点和候选快照。

### 原位应用

批准后使用既有 `registry.sample_subject_resolution_batch`、`item`、`revision` 和数据库函数追加解析修订：

- 规范样本点 ID 保持不变；
- 原业务记录 ID 和事实值保持不变；
- 每条来源记录追加指向规范样本点的解析修订；
- 批次、项目、前后摘要、操作人和时间均可审计；
- 旧解析不删除，既有回滚能力保留。

旧样本点主数据不物理删除。总揽和下游查询按当前解析取得规范样本点，避免重复计数。

## Web 信息架构

现有“我的工作 → 样本点治理”扩展为同一业务入口下的两个独立区块：

- “坐标治理”：保留当前全部功能和文案。
- “身份治理”：包含“身份待核验”“历史重复归并”“任务历史”。

业务页面不展示开发术语、SQL、散列或内部异常。样本点 ID 以“系统编号”展示，并配合姓名、地区和坐标帮助判断。

身份待核验卡片并排显示本次行和历史候选，联系方式脱敏。操作必须填写依据。状态变更通过现有实时业务事件触发刷新；页面刷新或重登后仍可恢复。

## 实时联动

身份核验草稿不是正式数据，因此不进入总揽、产情分析、市场分析和供需。晋级并审核通过后继续使用原有业务事件与核定数据查询链。

历史归并只改变当前身份解析，不改业务事实。预期可见变化是重复样本点数量下降、重复计数被纠正；价格、面积、产量、库存等来源事实不得改变。缺失数据仍为缺失。

## 权限与安全

- 读取候选要求 `BUSINESS_READ` 和地区范围。
- 创建核验决定要求草稿所有者或受权业务管理员。
- 历史归并导出/上传要求 `BUSINESS_IMPORT`。
- 归并审核与应用要求 `BUSINESS_APPROVE`。
- 所有目标样本点必须处于当前账号授权地区，服务端重新校验，不信任客户端候选列表。
- 所有决定使用版本快照、事务锁与幂等键；过期、重复或越权请求返回明确的 409/403 业务响应。

### 数据库迁移边界

- V129 只建立以公开姓名、联系方式和受管样本点为依据的有效记录视图，并退役普通业务目录中的隐藏治理输入；不删除原始核定台账。
- V130 的 `SECURITY DEFINER` 函数从不可变提交与审核事件重建所有可变参数，运行账号不能直接写解析批次，也不能绕过审核调用底层应用函数。
- V131 只向 V130 的 NOLOGIN 迁移所有者授予嵌套市场事实校验所需的 `SELECT`；不向运行账号增加表权限。
- 三个迁移必须同时通过空库迁移、从可信旧版本升级回放、最小权限与身份归并集成测试，才允许进入长期 `main`。

## 验收条件

### 后端

- 同名不同联系方式且证据明确时允许新建。
- 同名同联系方式唯一候选时复用同一稳定样本点 ID。
- 同名同联系方式多候选时只保留身份待核验草稿。
- 同身份同期间同数据不重复创建正式记录。
- 同身份同期间冲突数据进入待核验，不覆盖既有记录。
- 人工链接、确认不同、退回修改、过期决定、越权和幂等重放均有定向测试。
- 普通职责分离与平台唯一所有者例外均有测试。
- 历史归并批准后，原记录 ID/事实不变，当前解析指向规范样本点，审计完整。

### Web

- 待核验列表、候选对比、三种决定、必填依据、错误恢复和实时刷新有组件测试。
- 坐标治理原组件测试保持通过。
- 导入任务能够区分“身份待核验”和真正失败，不把整份任务标成失败。

### 受管副本

- JDK 21 定向后端测试使用 `qiqihar_enterprise_test`。
- Node 24 定向组件测试与 `tsc -b && vite build` 通过。
- 63182/8090 使用受管副本验证正常行、待核验行、决定后晋级、业务审核、实时刷新与下游重查。
- 浏览器控制台无新增错误或警告。

## 明确不做

- 不依据姓名自动合并。
- 不新增 V129–V131 之外的身份迁移、通用身份表或简单唯一索引。
- 不修改供需、照片、导入任务信息架构或报告中心。
- 不删除历史业务记录或主数据。
- 不使用云端、生产或付费地图服务。
